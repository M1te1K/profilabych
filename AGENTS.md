# Профилабыч: инструкции для разработки

## Назначение и границы

Профилабыч — модульный Telegram AI-агент для тестового задания AI-разработчика.
Первый продуктовый вариант: агент с несколькими инструментами, историей диалога
и пользовательскими заметками. Product Owner определяет требования и принимает
архитектурные решения; разработчик самостоятельно выполняет техническую работу.

Сейчас реализован этап 2: Agent Core, адаптер OpenRouter, Tool Registry, инструменты,
SQLite-история/заметки и CLI. Реальные API-запросы на этапе 2 не выполнялись.
Telegram polling и представление ответов реализуются следующим этапом.
RAG, PDF, мультиагентность, постоянная AI-память, ReAct и голос — только будущие
расширения. Не добавлять их без нового требования. Не создавать дополнительных
AI-агентов без отдельного требования.

## Стек и архитектура

- Python 3.12+ (до 3.15), aiogram 3, OpenRouter, бесплатная Qwen с Tool Calling.
- SQLite через aiosqlite, HTTP через httpx, конфигурация через pydantic-settings.
- pytest, Ruff и mypy; Docker; Git. Разработка на Apple Silicon M1, 8 ГБ RAM.
- `src/profilabych/interfaces/telegram/`: команды, сообщения, представление ответа.
- `src/profilabych/interfaces/cli.py`: локальный ввод, /reset и /exit, без бизнес-логики.
- `src/profilabych/agent/`: диалог и последовательный цикл вызовов инструментов.
- `src/profilabych/llm/`: контракт провайдера и адаптер OpenRouter.
- `src/profilabych/tools/`: описание, регистрация и исполнение инструментов.
- `src/profilabych/storage/`: история, заметки и SQLite-репозитории.
- `src/profilabych/config.py`: загрузка и проверка настроек.
- `src/profilabych/logging.py`: структурированные логи и маскирование секретов.
- `src/profilabych/main.py`: точка сборки зависимостей и запуска.

Ядро не зависит от aiogram и HTTP-клиента. Адаптеры не управляют диалогом.
Зависимости передавать через конструкторы/аргументы; не создавать глобальные
клиенты, контейнеры DI, фабрики и базовые классы без практической необходимости.
Модель выбирается конфигурацией; смена Qwen на доступную бесплатную DeepSeek
не должна менять ядро. Подробные границы — в `docs/architecture.md`.

## Код

- Соблюдать SRP и Separation of Concerns; предпочитать небольшие модули.
- Type hints обязательны для функций и публичных интерфейсов.
- Асинхронный I/O через async/await; не блокировать event loop синхронным HTTP/SQL.
- На импорте не читать настройки, не открывать БД и не обращаться к сети.
- Обрабатывать ожидаемые ошибки на границах системы; не скрывать ошибки широким
  `except Exception`. Не подавлять отмену asyncio-задач.
- Сохранять понятные имена и короткие docstrings. Не добавлять фиктивные реализации,
  которые возвращают успех вместо ещё не реализованного поведения.
- Менять архитектуру только по необходимости; существенные решения согласовывать
  с Product Owner, описав конкретную проблему и подготовленный вариант решения.

## Безопасность и бюджет

- Бюджет 0 рублей. Не выполнять платные операции и не включать платные модели
  без явного разрешения Product Owner. Тяжёлые модели локально не запускать.
- Секреты только в переменных окружения или локальном `.env`; пример без секретов.
- Не читать/печатать реальные ключи при диагностике, не логировать настройки целиком,
  заголовки Authorization, токены и сырые HTTP-запросы/ответы.
- По явному требованию этапа 2 запрос/ответ пользователя, аргументы и результаты
  инструментов логируются ограниченно. Использовать существующий JSON formatter:
  маскирование до усечения, 1000 символов/поле, 20 элементов/коллекцию, глубина 6.
  Логи содержат пользовательские данные и требуют локального контроля доступа.
- Передавать известные секреты системе маскирования при настройке логирования.
  Маскирование — дополнительная защита, а не разрешение логировать секреты.
- При интеграции OpenRouter проверять поддержку tools и нулевую стоимость,
  использовать `provider.max_price` с нулевыми prompt/completion/request,
  `require_parameters=true`; не добавлять платный fallback.
- `:free` в конфигурации — проверка выбора модели, а не гарантия её доступности.
- Во всех операциях хранения и инструментах обязателен доверенный `user_id`,
  полученный от Telegram, а не от LLM. Разделять также диалоги по `chat_id`.
- SQL только параметризованный. Не использовать `eval()` и `exec()` для вычислений.
- Проверять аргументы инструментов, ограничивать число вызовов и время выполнения.
- Не более 5 раундов tools; отдельный общий лимит вызовов по умолчанию 5.
  Сохранять tool_call_id и порядок результатов. Историю обрезать целыми ходами.
- Запросы/reset одного пользователя проводить через один Agent на приложение.
  Сериализация действует в одном процессе; multi-process/crash recovery не реализованы.
- reset_history удаляет только историю, заметки остаются. ToolContext доверенный,
  идентификаторы не входят в JSON Schema инструментов заметок.

## Проверки

- Unit-тесты без внешней сети и реальных ключей; использовать временные файлы
  и окружение. Для HTTP — MockTransport; для БД — временная SQLite.
- Обязательно проверять конфигурацию, безопасность логов и локальный запуск.
  Сохранять тесты цикла tools, лимитов, ошибок, изоляции и конкурентности данных.
- Локальный offline запуск: `python -m profilabych --check` и `--demo`.
  Обычный запуск — CLI с ключом и сетевым preflight; не использовать для диагностики
  без отдельного разрешения на реальные API-запросы.
- После изменений запускать `.venv/bin/python -m pytest`,
  `.venv/bin/python -m ruff check .`, `.venv/bin/python -m ruff format --check .`,
  `.venv/bin/python -m mypy src`, `.venv/bin/python -m pip check`.
- Не заявлять об успешных проверках, которые фактически не запускались.
- При изменении зависимостей обновлять lock-файлы requirements и проверять установку.

## Git и файлы

- Сохранять пользовательские файлы и несвязанные изменения. Не использовать
  разрушительные reset/clean и не перезаписывать существующий `.env`.
- Не коммитить `.env`, ключи, окружения, SQLite, логи, кеши и временные файлы.
- Новые ветки по умолчанию `codex/…`. Не выполнять push без разрешения.
- Коммиты делать по запросу или согласованному процессу; перед коммитом проверять diff.
- Инструкции пользователя имеют приоритет. Не просить выполнять команды или
  создавать файлы вручную, если разработчик может сделать это самостоятельно.
